## 1. 背景与用户痛点

用户原始工作流：用 superpowers 生成 `specs/` 下的方案文件 → 打开 **4 个终端窗口** → 分别启动 `product-reviewer` / `system-critic` / `test-designer` 三个角色审核 → 把输出复制到 `review-orchestrator` 合并 → 交给 superpowers 决定采纳与否。

用户期望目标态：

1. 只开 **1 个终端窗口**
2. 只说 **一次** 审核要求
3. 三个角色 **独立分开** 审核
4. 审核产物输出到 superpowers 风格的文件夹（类似 `plans/`、`specs/`）
5. 命名规则对齐 superpowers 惯例
6. 最终 **合并成一个文档**
7. 让 superpowers **自动阅读** 该审核文档
8. 标记三个角色的发现中 **哪些采纳 / 哪些不采纳**
9. 打上标记，支持 **统计分析、迭代升级**

本报告评估 v2 对上述 9 条诉求的覆盖度，并列出残留 / 新引入缺陷。

### 🟠 P1

#### D-002 · `templates/consolidated-review.md` 决策词汇 4–5 套并存
同一"决策"概念，全文件至少出现 5 种命名：

| 位置 | 用词 |
|------|------|
| 第 204–208 行（Finding Status） | `ACCEPTED / REJECTED / DEFERRED / PARTIALLY_ACCEPTED / DUPLICATE`（缺 INVALIDATED、缺 PENDING_DECISION） |
| 第 762 / 774 / 914 行（Superpowers Instructions / 决策选项） | `ACCEPTED / REJECTED / DEFERRED / PARTIALLY_ACCEPTED / DUPLICATE / INVALIDATED` |
| 第 868 行（Decision Records 骨架） | `ACCEPT / REJECT / DEFER / MODIFY / DUPLICATE / SUPERSEDE / RESOLVE`（完全不同的动词集） |
| 第 955 / 961 行（Review Statistics By Status） | `Ready for Decision` / `Represented Elsewhere`（短语式） |

后果：用户诉求 #8（标记采纳/不采纳）的核心动作没有唯一标准词，superpowers 与人工都无法稳定标记；统计分析（#9）因无统一枚举而无法聚合。
**修复建议**：以 `decision-protocol.md` 的权威 7 态（`PENDING_DECISION / ACCEPTED / REJECTED / DEFERRED / PARTIALLY_ACCEPTED / DUPLICATE / INVALIDATED`）为唯一真相源，全文统一；删除 `MODIFY/SUPERSEDE/RESOLVE` 等非标词；`decision_status` 仅保留 `PENDING_DECISION / COMPLETED` 两态。

#### D-003 · `CONFIRMED_GAP` 无合同出处
`roles/test-designer.md`（164 / 726 / 819 行）与 `templates/test-review.md`（94 / 179 / 343 行）广泛使用 `CONFIRMED_GAP` 作为证据类；但 `protocols/finding-protocol.md` 的 Evidence Class 仅定义 `CONFIRMED_DEFECT / MATERIAL_RISK / DESIGN_PREFERENCE`（第 128 / 140 / 151 行），**完全没有 `CONFIRMED_GAP`**。

后果：Test Designer 的产物违反"统一 Finding 契约"，合并阶段（review-orchestrator）按契约校验时会判定该证据类非法。
**修复建议**：在 `finding-protocol.md` Evidence Class 中补 `#### CONFIRMED_GAP`（语义：已确认的验证缺口，对应 Test Designer 的产出），使三方契约闭合。

#### D-004 · P3 严重度死路
严重度枚举含 `P3`，但 `decision-protocol.md` 没有任何针对 P3 的决策分支——P3 发现既不被要求决策，也不被自动归并，处于"既不采纳也不拒绝"的真空态。
**修复建议**：二选一——① 从严重度枚举移除 P3；② 显式定义 P3 = 信息性观察、无需决策（decision_status 直接置 `INVALIDATED` 或标注 `OBSERVATION`）。

#### D-005 · 关系分类 7 类 vs 4 类矛盾
`protocols/consolidation-protocol.md`（Section 6）定义 7 类关系：`DUPLICATE / SAME_ROOT_CAUSE / RELATED / INDEPENDENT / CONTRADICTORY / SUBSET / CONSEQUENCE`；而 `protocols/finding-protocol.md` 使用 4 类子集。两处对"发现间关系"的定义不一致，合并阶段引用时易混淆。
**修复建议**：以 consolidation-protocol 的 7 类为唯一权威，finding-protocol 改为引用而非重定义，或显式声明"关系分类以 consolidation-protocol 为准"。
